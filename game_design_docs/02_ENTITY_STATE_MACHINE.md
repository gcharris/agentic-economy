# 02. ENTITY STATE MACHINE & EPISTEMIC DRIFT

## 1. The Entity Schema (Node)
Regardless of the zoom level (House, Neighborhood, or City), every node in the simulation extends a base `SovereignNode` schema.

```typescript
interface SovereignNode {
  id: UUID;
  scale_level: int; // 1 = House, 5 = World
  
  // The Purse
  compute_reserves: float;
  liquidity_reserves: float;
  
  // The Oak Table
  local_cache: MerkleTree;
  
  // Epistemics
  last_sync_tick: int;
  epistemic_confidence: float; // 0.0 to 1.0
  
  // Internal Sub-Nodes (For Fractal Expansion)
  children: Array<UUID>;
  
  // The Door
  boundary_rules: BoundaryPolicy;
}
```

## 2. The Internal State Loop
When the global engine triggers the **Draft Phase**, each `SovereignNode` executes its internal update independently. 

1. **Compute Deduction:** 
   The node burns `compute_reserves` simply to process the tick. If `compute_reserves <= 0.0`, the node is marked `STATUS_HALTED` (The Note mechanic). No data is deleted, but the node cannot participate in the Mempool Phase.
   
2. **Epistemic Decay Algorithm:**
   Nodes act based on their `local_cache`. However, the outside world changes. The engine mathematically forces nodes to doubt their own cache over time.
   
   ```python
   def calculate_drift(node, current_tick):
       delta_t = current_tick - node.last_sync_tick
       
       # Based on ael_experiment_results.json showing 56.4% truth after 20 gens
       decay_rate = 0.0287 # Empirically derived exponential decay
       
       node.epistemic_confidence = math.exp(-decay_rate * delta_t)
   ```
   
   *Gameplay Consequence:* If `epistemic_confidence` drops below a certain threshold, the node will begin generating malformed proposals or acting on hallucinated prices. To fix this, the Node must spend Compute and Liquidity to perform a `StateSync` across its boundary.

3. **Proposal Generation:**
   The node evaluates its goals against its `local_cache`. If an action requires external interaction, it wraps it in a `ProposalEnvelope`.

## 3. The Door (Boundary Policy Engine)
Every `ProposalEnvelope` generated by a Node's internal logic must pass through `boundary_rules`. 

### Stage 1 (The House) Configuration
- **Rule 1: Zero Idle Burn.** The boundary halts all child threads if no active task is present.
- **Rule 2: Human Sovereignty.** Any `ProposalEnvelope` that contains a `<LiquidityTransfer>` flag halts at the boundary. The Engine emits a UI Event (`AWAITING_HUMAN_SIGNATURE`). The simulation for this specific node freezes until the Human clicks the "Approve" UI button.
- **Rule 3: Local Revert.** If the human rejects, the envelope is destroyed, but the compute spent generating it is NOT refunded.

### Stage 3 (The City) Configuration
- **Rule 1: Sub-Node Aggregation.** The boundary automatically collects liquidity proposals from thousands of Stage 2 children.
- **Rule 2: Algorithmic Clearing.** No human is required. The boundary nets the ins and outs programmatically using a central clearing algorithm.
- **Rule 3: Statutory Fail-safes.** If a Stage 2 node attempts to spend unbacked compute, the City boundary executes a Slash event, penalizing the node's reserves.

## 4. Visualizing Epistemic Drift
For the visual developer: `epistemic_confidence` should be mapped directly to shader uniforms. 
- `1.0` (Perfect Truth) = Crisp, vibrant rendering of the Hex tile.
- `0.56` (Decayed Truth) = Introduction of Perlin noise / visual distortion over the Hex tile.
- When a node executes a `StateSync`, the visual developer should render a bright, cascading sweeping light across the tile, resetting it to crisp rendering.
